## 预案一：Supabase断供（极高风险）

### 场景A：Supabase Inc.政策变化（账号被封/服务终止）

#### 迁移目标
- **新数据库**：Supabase自托管（Hetzner/阿里云）+ Supabase自托管版
- **预计迁移时间**：3-7天
- **数据丢失风险**：最后备份之后的数据

#### 迁移步骤

**第1步：准备新数据库（1-2天）**

1. 租用服务器（推荐Hetzner CX31，€10/月，4GB RAM）
2. 安装Docker + 运行Supabase自托管版
   ```bash
   git clone https://github.com/supabase/supabase
   cd supabase/docker
   docker compose up -d
   ```
3. 配置域名 + SSL证书
4. 验证新数据库可用

**第2步：数据迁移（1天）**

1. 从最后备份恢复数据到新数据库
   ```bash
   psql $NEW_DB_URL < backups/backup-YYYY-MM-DD.sql
   ```
2. 验证数据完整性（表数量、行数）
3. 修改`.env.local`中的Supabase URL和Key
4. 本地测试连接新数据库

**第3步：切换生产环境（1天）**

1. 在Vercel中更新环境变量：
   - `NEXT_PUBLIC_SUPABASE_URL` → 新URL
   - `NEXT_PUBLIC_SUPABASE_ANON_KEY` → 新Key
   - `SUPABASE_SERVICE_ROLE_KEY` → 新Service Key
2. 触发重新部署
3. 生产验证（登录、核心功能）

**第4步：通知用户（1天）**

1. 发送邮件/短信通知用户"系统维护完成"
2. 提供临时访问方案（如有）
3. 收集用户反馈

#### 迁移成本

| 项目 | 成本 |
|------|------|
| 服务器（Hetzner CX31） | €10/月 |
| 域名 + SSL | 免费（用现有） |
| 工程师时间 | 3-7天 |
| **总计** | **€10/月 + 3-7天工期** |

### 场景B：Supabase数据库崩溃（数据损坏/丢失）

#### 恢复步骤

**第1步：确认崩溃范围（1小时）**

1. 登录Supabase Dashboard → 检查数据库状态
2. 尝试简单查询（如`SELECT * FROM users LIMIT 1`）
3. 确认是"部分损坏"还是"全部丢失"

**第2步：从备份恢复（2-4小时）**

1. 进入 Supabase Dashboard → **Settings** → **Database**
2. 点击 **Restore from backup**
3. 选择最近的备份（最好是过去24小时内）
4. 确认恢复（会覆盖当前数据！）

**第3步：验证数据完整性（1-2小时）**

1. 检查表数量：`SELECT tablename FROM pg_tables WHERE schemaname='public';`
2. 检查行数：`SELECT COUNT(*) FROM users;`
3. 检查最近数据：`SELECT * FROM users ORDER BY created_at DESC LIMIT 10;`

**第4步：如果备份也损坏 → 从GitHub Actions备份恢复（4-8小时）**

1. 下载GitHub Actions Artifact中的最新备份文件
2. 本地恢复：`psql $DB_URL < backup-YYYY-MM-DD.sql`
3. 验证后推送到Supabase

#### 数据丢失预估

| 备份频率 | 最长丢失时间 | 丢失数据量（假设100用户/天） |
|------------|----------------|----------------------------|
| 每日备份 | 24小时 | 最多1天的数据 |
| 每周备份 | 7天 | 最多7天的数据 |

**结论**：必须每天备份！

- **风险**：Coze突然停止服务，无法部署更新
